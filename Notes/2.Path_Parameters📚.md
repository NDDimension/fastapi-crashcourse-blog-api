# 🧭 FastAPI — Break It Down + Path Parameters

> **In this note:** Understanding FastAPI’s structure, how path parameters work, and how to design clean, REST-friendly URLs.

---

### 🧩 Summary

**What you’ll learn**

- How a FastAPI app is structured (route → handler → response)
    
- What path parameters are, how typing and validation work, and how they appear in docs
    
- Common pitfalls and best practices when designing URL paths
    

---

### 🏗️ Anatomy of a FastAPI Endpoint

- **App:** Create an application instance to hold all routes (called _path operations_).
    
- **Path operation:** A function mapped to a method + path (e.g., `GET /`, `GET /blog/{id}`).
    
- **Response:** Return Python data (`dict`, `list`, etc.) — automatically converted to JSON.
    
    - Default status: `200 OK`
        
- **Docs:** Every route appears in interactive docs:
    
    - Swagger UI → `/docs`
        
    - ReDoc → `/redoc`
        

---

### 🔤 Path Parameters 101

- **Definition:** A variable segment inside the URL, written as `/resource/{param}`.
    
- **Purpose:** Identifies a specific resource (e.g., `/blog/{id}` → one blog).
    
- **Always required:** Path parameters **cannot** be optional.
    
- **Naming rule:** The placeholder name in the path **must match** the function parameter name.
    

---

### 🧮 Typing, Validation, and Conversion

- **Type hints = validation rules**
    
    - `int` → only digits accepted; invalid → `422 Unprocessable Entity`
        
    - `str` → any text (URL-decoded)
        
    - `float`, `UUID`, `datetime` → supported and validated
        
- **Docs integration:** Typed params appear in OpenAPI as `in: path` with their correct type.
    
- **Untyped params:** Default to `string` (lose numeric/date validation).
    
- **Advanced constraints:** Enforce ranges, lengths, and descriptions
    
    - e.g., “`id` must be ≥ 1”
        

---

### 🧭 Designing REST-Friendly Paths

- Use **nouns** for resources:  
    `/blogs`, `/blogs/{id}`, `/blogs/{id}/comments`
    
- Keep paths **stable and hierarchical** — deeper resources → deeper paths.
    
- Prefer **specific static routes** over ambiguous ones:
    
    - ✅ `/blogs/create`
        
    - 🚫 `/blogs/{id}`
        
- Note: Static paths take precedence, but clear naming avoids confusion.
    

---

### 🧪 What You’ll Observe in Practice

- **Type conversion:** `/blog/5` → integer `5` when annotated as `int`.
    
- **Validation errors:** `/blog/abc` (expecting `int`) → `422` with clear error message.
    
- **JSON encoding:** Return JSON-serializable types only.
    
    - Sets → converted to lists (order not guaranteed).
        

---

### 📚 Docs & Developer Experience

- Interactive docs allow testing routes instantly.
    
- Path parameters show their types and `"required": true`.
    
- Excellent for onboarding and testing without external tools.
    

---

### ⚠️ Common Gotchas

- **Trailing slash matters:** `/blogs` ≠ `/blogs/` — pick one style and stay consistent.
    
- **Name mismatch:** `{id}` in the path must match the function argument name.
    
- **Overlapping routes:** Avoid overly generic routes (e.g., `/{slug}`) that capture everything.
    
- **Capturing slashes:** Use `{file_path:path}` to capture full paths (including `/`).
    

---

### ✅ Best Practices Checklist

-  Use clear, plural resource names → `/blogs`, `/blogs/{id}`
    
-  Type all path parameters (`int`, `UUID`, `datetime`, etc.)
    
-  Use **query params** for filtering, sorting, pagination → `/blogs?search=...&limit=10`
    
-  Return only JSON-serializable data (prefer lists over sets)
    
-  Document constraints (`min`, `max`, etc.) and meanings in parameter descriptions
